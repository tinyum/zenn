## スロークエリはレビューで見つからない

参画中のサービスには、数億レコード規模の巨大テーブルがあります。  
このテーブルへのクエリは、実際に実行してみないとどのインデックスが選ばれるか、実行プランが確定しません。

開発環境の DB は小さいので、どのテーブルに何行あるのかすら分かりません。  
つまり、コードだけを見る AI レビューでも人間のレビューでも、クエリ性能の問題は原理的に指摘できないのです。

実際、負荷改善を繰り返しても、新機能の追加や改修を重ねるうちにレスポンスが定期的に悪化することがあり、その都度の対応に手間がかかっていました。

当時の運用はこうでした。

- 複雑なクエリを含む PR は毎回自分がレビューする
- 本番相当の DB にいろいろな EXPLAIN クエリを投げて問題ないかを確かめる

レスポンスが遅いクエリの改善を何度もやる中で、毎回自分の手でクエリを投げて調べるのが面倒になってきました。  
「自分がやっていることをそのまま自動化すればいい」と考えたのが、この仕組みの始まりです。

## LLM エージェントに DB を渡して EXPLAIN ANALYZE させる

人間のレビュアーがやっていたことを分解すると、こうなります。

1. diff からクエリの変更を見つける
2. テーブル構造とインデックスを確認する
3. 実データでありそうなパラメータを探す
4. EXPLAIN ANALYZE を実行して実行計画を読む
5. 危険なら指摘する

これは LLM エージェントの tool-use ループでそのまま再現できます。  
tool-use ループとは、LLM にツール（関数）の一覧を渡し、「LLM がツールを呼ぶ → こちらが実行して結果を返す → LLM が結果を見て次の行動を決める」を繰り返させる仕組みです。人間のレビュアーの試行錯誤を、そのまま LLM にやらせるイメージです。

```
diff + ソースコード + スキーマ情報
    |
    v
LLM エージェント（tool-use ループ）
    |-- describe_table   → テーブル構造・インデックスを確認
    |-- run_sql          → SELECT で実データのパラメータ候補を取得
    |-- explain_analyze  → EXPLAIN ANALYZE を実行
    |-- エラーが出たら LLM が自分で修正して再試行
    |
    v
性能レポート（Markdown）→ PR コメント + ブロッキング判定
```

接続先は本番相当のデータ分布を持つ DB なので、実行計画も本番と同じものが得られます（DB の詳細は次の章で）。

これを GitHub Actions で PR ごとに実行し、結果を PR コメントに投稿します。こんな形です。

> ## クエリ分析結果
>
>
> | #   | クエリ概要         | 実行時間    | スキャン方式     | 評価  |
> | --- | ------------- | ------- | ---------- | --- |
> | 1   | 対象テーブルの更新履歴の取得 | 1.344ms | Index Scan | 高速  |
>

問題がなければこれで終わり。問題があれば CI が落ちて、レポートに理由が書かれます。

## LLM に本物の DB を触らせるための安全設計

LLM が生成した SQL をそのまま DB に流すので、安全対策は多層にしています。

大前提として、接続先は本番 DB ではありません。本番データを定期同期したマスク済み DB なので、万一おかしなクエリが走っても本番サービスには影響しません。  
その上で、DB 側とアプリ側の両方にガードを入れています。

- **READ ONLY トランザクション**: すべてのクエリを `BEGIN READ ONLY` + `SET LOCAL statement_timeout = '10s'` の中で実行
- **SQL ホワイトリスト**: SELECT / EXPLAIN / WITH 文のみ許可。DDL/DML と複数文は拒否
- **コメント除去の堅牢化**: SQL コメントやドル引用を悪用したホワイトリスト回避を防ぐ
- **プレースホルダー検証**: LLM が `12345678-1234-...` のような架空の UUID で EXPLAIN しようとしたら拒否し、実データから取り直させる
- **反復回数の上限**: tool-use ループは最大20回で打ち切り

もう一つ大事なのが、**失敗時は非ブロッキングに倒す**ことです。  
分析自体のエラー（LLM の失敗、タイムアウト等）では CI を落とさず、警告だけ出して通します。

CI を落とすのは「危険なクエリを検出したとき」だけ。  
ここを間違えると、ツールの不調で開発全体が止まり、誰も使ってくれなくなります。

## LLM の「問題ありません」を信じてはいけなかった

導入からしばらくして、見逃しが発覚しました。  
**数十万行を読む実質フルスキャンのクエリを、LLM が「Index Scan を使用しているので問題ありません」と評価して CI を通していた**のです。

実行計画上は確かに Index Scan でした。  
しかし Index Cond（絞り込み条件）がなく、インデックス全体を舐めているだけ。実態はフルスキャンと同じです。

LLM は実行計画を読み解けても、「これを blocking にすべきか」の判定まで任せると、もっともらしい理由をつけて見逃すことがある。  
これが運用して分かった一番の学びです。

対策として、**判定を LLM から取り上げて、EXPLAIN の JSON をコードで機械判定する**方式に変えました。

- 1万行以上をスキャンする Seq Scan → blocking
- Index Cond のない Index Scan / Index Only Scan → blocking
- 実行時間3秒以上のクエリ → blocking

LLM の仕事は「調査とレポート生成」に限定し、CI を落とすかどうかはコードのルールで機械的に判断する。  
この役割分担にしてから、見逃しはなくなりました。

## マージ前に止まったクエリたち

機械判定に切り替えてから、実際にマージ前にブロックされた例をいくつか紹介します。

**例1: ILIKE 前方一致検索が数十万行の Seq Scan**

管理画面に検索機能を追加する PR で、`ILIKE '12345%'` の前方一致検索が追加されました。  
LLM のレポート上の評価は「良好」（実行時間 97ms）でしたが、機械判定が **数十万行の Seq Scan** を検出して CI をブロック。

> **blocking** - 大規模な実質フルスキャン、または3秒以上のクエリを検出しました。
>
> - 対象テーブル: Seq Scan / 数十万行を読み取り

開発者は指摘を受けて検索を完全一致に変更し、CI が通ってマージされました。  
「今は 97ms でも、フルスキャンはデータ増加で必ず遅くなる」という将来の障害を、レビュアーの介在なしで防げた例です。

**例2: 数百万行規模の中核テーブルを Seq Scan**

あるドメインの中核データを扱う改修 PR で、インデックスのないカラムでの検索が追加され、**数百万行の Seq Scan**（181ms）を検出してブロック。  
開発者がクエリ経路自体を見直し、インデックスの効くカラムでの取得に変更して解決しました。

どちらも共通しているのは、**私がレビューに入っていない**ことです。  
CI が指摘し、PR の作者が自分で直す。以前は私が手動でやっていたレビューと EXPLAIN の検証が、完全に自動で回っています。

こうした仕組みを CI に組み込むかどうかの判断も、既存の開発フローを変える提案も、特に制約なく進められました。裁量を持って技術的課題に取り組める環境はフリーランスとしてとてもありがたいと感じています。

## 運用コスト

- 起動回数: 月4,000〜5,000回（PR の open / synchronize ごとに実行）
- OpenAI API 費用: 月300ドル程度（1回あたり10円弱）
- 実行時間: タイムアウト15分、同一 PR の連続 push は concurrency で自動キャンセル

月300ドルは安くはありませんが、スロークエリが本番に流出したときの障害対応・調査・改修のコスト、そして毎回のレビューにかかっていた自分の時間と比べれば、十分に元が取れています。

## まとめ

- クエリ性能の問題は、本番相当のデータがないと原理的にレビューできない
- 人間のレビュアーがやっていた「EXPLAIN ANALYZE で確かめる」作業は、LLM エージェント + 3つのツールで自動化できる
- ただし blocking の判定は LLM に任せず、EXPLAIN の JSON をコードで機械判定する
- 失敗時は非ブロッキングに倒し、開発を止めない

自分が手でやっていた検証作業を課題として捉え、仕組みに変えたことで、チーム全体の資産になりました。  
同じように「毎回自分がやっているレビューや検証」があるなら、それはたぶん自動化のチャンスです。
